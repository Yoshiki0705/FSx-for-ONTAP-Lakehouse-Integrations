# ADR-004: Avoid Direct Dependency on S3 Access Points for Databricks Integration

## Status

**Accepted** — 2026-06-07

## Context / コンテキスト

This project's prior validation (fsxn-lakehouse-integrations blog series, Parts 1–7) discovered that Databricks Unity Catalog does not support S3-compatible endpoints (including FSx for ONTAP S3 Access Points) as external locations. The session policy applied during AssumeRole does not include the S3 AP ARN pattern, blocking object-level operations. The manufacturing data platform architecture must avoid this known limitation.

本プロジェクトの先行検証（fsxn-lakehouse-integrations ブログシリーズ、Part 1–7）により、Databricks Unity Catalog が S3 互換エンドポイント（FSx for ONTAP S3 アクセスポイントを含む）を外部ロケーションとしてサポートしないことが判明。AssumeRole 時に適用されるセッションポリシーが S3 AP ARN パターンを含まず、オブジェクトレベル操作がブロックされる。製造データプラットフォームアーキテクチャはこの既知の制限を回避する必要がある。

## Decision / 決定

The architecture will NOT depend on S3 Access Points for the Databricks integration path. Delta Lake tables will be stored on native Amazon S3, and data will flow to Databricks via Kafka Structured Streaming (not via direct FSx for ONTAP S3 AP access).

アーキテクチャは Databricks 統合パスで S3 アクセスポイントに依存しない。Delta Lake テーブルはネイティブ Amazon S3 に格納し、データは Kafka Structured Streaming 経由で Databricks に流れる（FSx for ONTAP S3 AP 経由の直接アクセスではなく）。

## Options Considered / 検討したオプション

| Option | Pros | Cons |
|--------|------|------|
| **Kafka → Structured Streaming → Delta on native S3** | Proven pattern; exactly-once; UC-governed; no S3 AP dependency | Requires streaming pipeline; data copied from source to S3 |
| FSx for ONTAP S3 AP as UC external location | Zero-copy access to existing data | **Not supported** — UC does not support S3-compatible endpoints (REF-020, REF-022) |
| FSx for ONTAP S3 AP with instance profile (bypass UC) | Direct access possible | Bypasses governance; PoC-only; not production-suitable |
| DataSync (FSx for ONTAP → S3) + UC external location | Data on native S3; UC-governed | Additional sync pipeline; latency; cost; data duplication |
| Databricks DBFS mount with NFS | Direct filesystem access | Blocked by the runtime seccomp BPF filter (`mount` returns EPERM here) |

## Consequences / 結果

### Positive / ポジティブ

- Architecture is immune to S3 AP limitations — uses only supported, production-proven patterns
- Delta tables are fully governed by Unity Catalog on native S3
- Kafka provides durable, replayable ingestion with exactly-once semantics
- No vendor support dependency — all components use documented, supported features
- Streaming ingestion provides near-real-time data freshness in Delta tables

### Negative / ネガティブ

- Data is copied from Kafka to S3 (not zero-copy from FSx for ONTAP)
- Payloads on FSx for ONTAP are not directly queryable from Databricks SQL — requires application-level access (boto3)
- If Databricks later supports S3 AP or S3-compatible endpoints, the architecture may have unnecessary indirection

## Risks / リスク

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Databricks adds S3 AP support in the future (making this decision overly conservative) | Low-Medium | Low | Decision can be revisited; current approach is strictly more reliable |
| Kafka → Delta pipeline adds latency vs zero-copy | Accepted | Low | Streaming latency (seconds) is acceptable for analytics use case |
| Payload access from Databricks requires separate auth path | Accepted | Low | Use boto3 + IAM role in notebook; document the pattern |
