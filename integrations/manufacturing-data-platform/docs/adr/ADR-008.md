# ADR-008: Edge Buffering and Failure Recovery Design

## Status

**Accepted** — 2026-06-07

## Context / コンテキスト

Manufacturing edge devices operate on factory networks that are inherently less reliable than cloud infrastructure. Network partitions, Kafka broker unavailability, and transient connectivity loss must not result in data loss. The edge layer must buffer events locally and forward them when connectivity is restored (store-and-forward pattern).

製造エッジデバイスは、クラウドインフラストラクチャよりも本質的に信頼性が低い工場ネットワーク上で動作する。ネットワーク分断、Kafka ブローカー不可用、一時的な接続性喪失がデータ損失につながってはならない。エッジレイヤーはイベントをローカルにバッファし、接続性が回復した時に転送しなければならない（ストアアンドフォワードパターン）。

This ADR addresses TSK-002 (Must Fix: Design Edge Buffering and Failure Recovery) from the design analysis in 07.

本 ADR は 07 の設計分析からの TSK-002（Must Fix：エッジバッファリングと障害復旧の設計）に対処する。

## Decision / 決定

Implement a **three-tier edge buffering architecture** combining:

1. **MQTT local broker** on the edge device (Raspberry Pi) for device-to-gateway communication
2. **Local persistent queue** (SQLite or filesystem) on the edge gateway for store-and-forward
3. **Kafka producer with built-in retry and idempotence** for edge-to-cloud delivery

**3層エッジバッファリングアーキテクチャ**を実装する：

1. デバイス-ゲートウェイ通信用のエッジデバイス（Raspberry Pi）上の **MQTT ローカルブローカー**
2. ストアアンドフォワード用のエッジゲートウェイ上の **ローカル永続キュー**（SQLite またはファイルシステム）
3. エッジ-クラウド配信用の **組み込みリトライとべき等性を持つ Kafka プロデューサー**

## Buffering Layers / バッファリング層

### Layer 1: Local MQTT Broker (Device → Gateway)

| Aspect | Design |
|--------|--------|
| Broker | Mosquitto on Raspberry Pi |
| QoS | QoS 2 (exactly-once within MQTT) |
| Persistence | SQLite (Mosquitto persistence DB) |
| Retention | Store messages until acknowledged by store-and-forward queue |
| Capacity | Limited by edge device storage (typically 16-64 GB SD card) |
| Protocol | MQTT 5.0 (session expiry, message expiry intervals) |

**Purpose**: Decouples sensor/PLC data collection from Kafka delivery. Sensors publish at their native rate regardless of Kafka availability.

### Layer 2: Store-and-Forward Queue (Gateway → Kafka)

| Aspect | Design |
|--------|--------|
| Implementation | SQLite WAL-mode database on edge gateway |
| Schema | `(id INTEGER PRIMARY KEY, timestamp INTEGER, topic TEXT, key BLOB, value BLOB, status TEXT, retry_count INTEGER, created_at INTEGER)` |
| Capacity | Configurable; default 10 GB (≈ millions of events at 1 KB avg) |
| Ordering | FIFO per topic, with retry prioritization |
| Dequeue | When Kafka producer reports delivery success (callback) |
| Overflow | When capacity reached: drop oldest OR write to local filesystem overflow |
| Monitoring | Expose queue depth, oldest undelivered event age, retry rate |

**Purpose**: Provides durable buffering that survives edge device restarts and extended network outages.

### Layer 3: Kafka Producer (Edge → Kafka Cluster)

| Configuration | Value | Rationale |
|--------------|-------|-----------|
| `enable.idempotence` | `true` | Prevents duplicates from retries |
| `acks` | `all` | Wait for all ISR replicas |
| `retries` | `2147483647` (max int) | Retry indefinitely |
| `retry.backoff.ms` | `1000` (initial) | Exponential backoff |
| `retry.backoff.max.ms` | `60000` (60s max) | Cap backoff |
| `delivery.timeout.ms` | `3600000` (1 hour) | Allow long retries during outage |
| `max.in.flight.requests.per.connection` | `5` | Allows pipelining with idempotence |
| `batch.size` | `65536` (64 KB) | Efficient batching |
| `linger.ms` | `100` | Slight delay for batching |
| `buffer.memory` | `67108864` (64 MB) | In-memory buffer before blocking |
| `compression.type` | `lz4` | Bandwidth optimization |

**Purpose**: The Kafka producer is the primary delivery mechanism. It handles transient failures internally. The store-and-forward queue handles extended outages that exceed the producer's buffer.

## Failure Scenarios / 障害シナリオ

### Scenario 1: Transient Network Glitch (< 30 seconds)

```
Timeline:
  T+0s:  Network blip occurs
  T+0s:  Kafka producer buffers in memory (buffer.memory = 64 MB)
  T+0s:  Producer retries automatically (exponential backoff)
  T+15s: Network recovers
  T+16s: Buffered messages delivered
  T+16s: Store-and-forward queue unaffected (messages never spilled)
  
Data Loss: NONE
Duplicates: NONE (idempotent producer)
```

### Scenario 2: Extended Network Outage (1-24 hours)

```
Timeline:
  T+0m:   Network fails
  T+0m:   Kafka producer buffers in memory
  T+1m:   Producer memory buffer fills (64 MB at high rate)
  T+1m:   Store-and-forward queue begins accepting overflow
  T+...    Sensors continue → MQTT broker → store-and-forward queue
  T+...    Queue grows (bounded by 10 GB capacity)
  T+8h:   Network restored
  T+8h:   Kafka producer resumes delivery
  T+8h:   Store-and-forward queue drains (FIFO order)
  T+9h:   Queue fully drained, normal operation resumes
  
Data Loss: NONE (if queue < 10 GB capacity)
Duplicates: NONE (idempotent producer)
Ordering: Maintained within same topic partition
```

### Scenario 3: Edge Device Restart

```
Timeline:
  T+0:  Edge device powers off (crash or maintenance)
  T+0:  In-flight Kafka producer messages lost (memory only)
  T+0:  Store-and-forward queue persists (SQLite WAL on disk)
  T+5m: Edge device restarts
  T+5m: Store-and-forward service starts
  T+5m: Reads undelivered messages from SQLite
  T+5m: Re-creates Kafka producer, resumes delivery
  T+6m: All buffered messages delivered
  
Data Loss: Only in-flight messages in Kafka producer buffer (< 64 MB)
Mitigation: Store-and-forward queue writes to disk BEFORE handing to producer
```

### Scenario 4: Kafka Cluster Completely Down

```
Timeline:
  T+0:   Kafka cluster unavailable
  T+0:   Producer retries hit delivery.timeout.ms (1 hour)
  T+1h:  Messages marked as undeliverable by producer
  T+1h:  Store-and-forward queue retains messages (no deletion on timeout)
  T+...   Queue continues growing
  T+24h: Kafka cluster recovered
  T+24h: Store-and-forward service retries queued messages
  T+25h: All messages delivered (order preserved)
  
Data Loss: NONE
Action Required: Monitor queue depth; alert if > 80% capacity
```

### Scenario 5: Payload Upload Failure

```
Timeline:
  T+0:  Camera captures quality image
  T+0:  Image saved to /tmp/payloads/img_xxx.jpg
  T+0:  Payload upload worker attempts NFS write to ONTAP
  T+0:  NFS mount unreachable
  T+1m: Retry #1 (exponential backoff)
  T+3m: Retry #2
  T+7m: Retry #3
  T+...  Continue retrying up to max_retries (default: 10)
  T+60m: If all retries fail → move to dead-letter directory
  T+60m: Alert: payload upload failed, manual intervention required
  
Rule: NO Kafka metadata event published until upload succeeds
Result: Delta table never references a non-existent payload
```

## Deduplication Strategy / 重複排除戦略

| Layer | Mechanism | Scope |
|-------|-----------|-------|
| MQTT | QoS 2 (exactly-once within MQTT session) | Device → Edge gateway |
| Kafka Producer | `enable.idempotence=true` (PID + sequence number) | Edge → Kafka broker |
| ClickHouse | `ReplacingMergeTree(event_id)` — dedup on merge | Kafka → ClickHouse |
| Databricks | `dropDuplicatesWithinWatermark("event_id")` OR foreachBatch + MERGE | Kafka → Delta |

### Event ID Design

```
event_id = f"{device_id}-{timestamp_ms}-{sequence_counter}"
```

- `device_id`: Unique per device (e.g., `factory-alpha-line-A1-sensor-001`)
- `timestamp_ms`: Unix timestamp in milliseconds
- `sequence_counter`: Monotonically increasing counter per device restart epoch

This makes event_id globally unique and deterministic (same event always produces same ID, enabling idempotent deduplication across all layers).

## Monitoring and Alerting / モニタリングとアラート

| Metric | Threshold | Alert |
|--------|-----------|-------|
| Store-and-forward queue depth | > 1M events OR > 5 GB | Warning: extended outage buffering |
| Queue depth | > 8 GB (80% capacity) | Critical: approaching capacity |
| Oldest undelivered message age | > 1 hour | Warning: delivery lag |
| Oldest undelivered message age | > 4 hours | Critical: investigate connectivity |
| Payload upload retry count | > 5 consecutive failures | Warning: storage connectivity |
| Payload dead-letter count | > 0 | Critical: manual intervention needed |
| Kafka producer error rate | > 10% of sends | Warning: broker issues |

## PoC Validation / PoC 検証

### Test Cases for Edge Buffering

| Test | Procedure | Expected Result |
|------|-----------|----------------|
| Normal operation | Generate 1000 events/sec for 60s | All events in Kafka, queue depth = 0 |
| Network disconnect (30s) | Disconnect network for 30s during generation | No data loss, brief queue buildup, auto-drain |
| Network disconnect (10 min) | Disconnect for 10 min at 100 events/sec | 60K events queued, all delivered after reconnect |
| Edge device restart | Kill process, restart after 60s | Queued events survive restart, delivered on resume |
| Kafka unavailable (1 hour) | Stop Kafka, generate events, restart after 1h | All events buffered locally, delivered after restart |
| Payload upload failure | Make NFS mount read-only during upload | No metadata event for failed payload; dead-letter alert |
| Queue overflow | Fill queue to capacity | Oldest events dropped (or overflow to filesystem) |
| Duplicate injection | Send same event_id twice | Single record in ClickHouse and Delta table |

## Options Considered / 検討したオプション

| Option | Buffering | Persistence | Complexity | Edge Overhead | Verdict |
|--------|-----------|------------|------------|---------------|---------|
| **MQTT + SQLite + Kafka idempotent** | 3-tier | ✅ Disk-based | Medium | Low (Raspberry Pi capable) | **Selected** |
| Embedded Kafka (KRaft) on edge | Kafka log | ✅ Disk-based | High | High (resource-intensive) | Rejected for PoC |

## Consequences / 結果

### Positive / ポジティブ

- Zero data loss during network outages up to queue capacity
- Deterministic deduplication across all layers (event_id)
- Payload integrity guaranteed (metadata published only after upload confirmed)
- Works on Raspberry Pi hardware constraints (SQLite is lightweight)
- Compatible with both Phase A (simulated) and Phase B (physical edge devices)
- Integrates with ONTAP-Edge-to-Cloud-AI project design

### Negative / ネガティブ

- Added complexity on edge device (MQTT + SQLite + Kafka producer)
- Local storage capacity limits buffering duration at high event rates
- SQLite write performance may limit throughput on SD cards (mitigate: use USB SSD)
- Need to handle edge device clock drift (NTP required)
- Queue overflow requires policy decision (drop oldest vs block)

## Design Review Notes / 設計レビューノート

> Notes recorded while checking this decision against the design concerns listed in [design concern checklist](../en/08_design_concern_checklist.md). Self-review, not external review.
>
> 本決定を[設計論点チェックリスト](../en/08_design_concern_checklist.md)に列挙した設計上の論点に照らして確認した際のメモ。セルフレビューであり、外部レビューではない。

- **Architecture soundness**: 3-tier buffering provides clear failure isolation. Idempotent producer eliminates duplicate risk. Store-and-forward scales to 10 GB = hours of buffering at typical manufacturing rates.
- **Edge and factory fit**: Addresses all identified failure scenarios. Payload upload rule (metadata only after confirmed upload) is critical and correctly enforced. Compatible with Raspberry Pi constraints. NTP clock sync requirement noted.
- **Catalog governance**: Deduplication at Databricks layer (dropDuplicatesWithinWatermark or MERGE) is appropriate safety net. event_id design is deterministic and suitable for dedup key.
- **Storage fit**: Payload write to ONTAP via NFS with retry and checksum is robust. Dead-letter pattern for failed uploads prevents orphaned metadata.
- **Confidentiality check**: No sensitive content. All device names and paths are synthetic/generic.
