# ADR-007: Phased Deployment Topology — AWS-First then Hybrid with Instaclustr On-Premises

## Status

**Accepted** — 2026-06-07

## Context / コンテキスト

The manufacturing data platform targets a hybrid edge-to-cloud architecture where the primary data generation and real-time analytics occur on-premises (factory floor), and governed analytics/AI runs in AWS (Databricks + Unity Catalog). The PoC must start on AWS while on-premises hardware is being procured, then transition to a hybrid model.

製造データプラットフォームは、主要なデータ生成とリアルタイム分析がオンプレミス（工場フロア）で行われ、ガバナンス付き分析/AI が AWS（Databricks + Unity Catalog）で実行されるハイブリッド エッジ to クラウド アーキテクチャを目標とする。PoC はオンプレミスハードウェアの調達中に AWS 上で開始し、その後ハイブリッドモデルに移行する必要がある。

Additionally, edge devices (Raspberry Pi) are being prepared in a separate project ([ontap-edge-to-cloud-ai](https://github.com/Yoshiki0705/ontap-edge-to-cloud-ai)) and will merge with this platform.

さらに、エッジデバイス（Raspberry Pi）は別プロジェクト（[ontap-edge-to-cloud-ai](https://github.com/Yoshiki0705/ontap-edge-to-cloud-ai)）で準備中であり、本プラットフォームと合流予定。

## Decision / 決定

Adopt a **two-phase deployment topology**:

**Phase A (Immediate):** All components on AWS for initial validation.
**Phase B (Target):** Instaclustr-managed Kafka + ClickHouse on-premises, with Databricks remaining on AWS. FSx for ONTAP (AWS) bridges to on-premises ONTAP when connected.

**2フェーズデプロイトポロジー**を採用する：

**フェーズ A（即時）:** 初期検証のため全コンポーネントを AWS 上に配置。
**フェーズ B（目標）:** Instaclustr マネージド Kafka + ClickHouse をオンプレミスに配置し、Databricks は AWS に維持。FSx for ONTAP（AWS）はオンプレミス ONTAP と接続時にブリッジ。

## Architecture: Phase B (Hybrid with Instaclustr) / フェーズ B（ハイブリッド + Instaclustr）

### Design Principle: No Unnecessary Data Duplication / 設計原則：不要なデータ多重持ちの排除

The architecture minimizes data copies across on-premises and cloud. Instead of replicating full payload data to AWS (SnapMirror = 2nd copy), we use **FlexCache** to provide on-demand caching in AWS. The authoritative data remains on-premises (single source of truth).

アーキテクチャはオンプレミスとクラウド間のデータコピーを最小化する。ペイロードデータ全体を AWS にレプリケーション（SnapMirror = 2重持ち）する代わりに、**FlexCache** を使用して AWS 側でオンデマンドキャッシュを提供する。正本データはオンプレミスに残る（単一の真実のソース）。

| Pattern | Data Copies | Use Case |
|---------|------------|----------|
| SnapMirror (rejected for primary path) | 2+ copies (on-prem + cloud) | DR/backup only |
| **FlexCache (selected)** | 1 origin + on-demand cache | Analytics access without duplication |
| Native S3 copy | 2+ copies | Not needed for payloads |

### FlexCache Data Flow / FlexCache データフロー

```
AI/ML workload on AWS needs payload:
  1. Query Delta table → get payload_uri (nfs://on-prem/vol/path)
  2. Access via FSx for ONTAP FlexCache volume
  3. FlexCache checks local cache:
     - HIT → return data immediately (low latency)
     - MISS → fetch from on-prem ONTAP origin (WAN latency, then cached)
  4. Subsequent accesses to same data → cache hit
  5. No permanent copy stored in AWS; cache evicted by LRU policy
```

### Why FlexCache over SnapMirror / SnapMirror ではなく FlexCache を選ぶ理由

| Criterion | FlexCache | SnapMirror |
|-----------|-----------|-----------|
| Data copies | 1 origin + cache (LRU eviction) | Full replica (2x storage cost) |
| Storage cost in AWS | Minimal (only hot/accessed data cached) | Full dataset size |
| Data freshness | On-demand (origin is always authoritative) | Async lag (RPO > 0) |
| Write-back support | ✅ (GA May 2025 on FSx for ONTAP) | N/A (one-way replication) |
| AI/ML payload access | Fetch on demand when model needs it | All data pre-replicated |
| Suitable for | Analytics access, read-heavy workloads | DR, backup, compliance |
| Data governance | Single source of truth (on-prem) | Two sources to govern |

## Rationale / 根拠

### Why Instaclustr for On-Premises / なぜ Instaclustr をオンプレに

1. **NetApp ecosystem alignment** [確認済み]: Instaclustr is a NetApp company. Using Instaclustr + FSx for ONTAP / on-prem ONTAP creates a unified NetApp data platform story.

2. **On-premises managed service** [確認済み]: Instaclustr supports deploying managed workloads on customer-provided on-premises infrastructure (Part 3 of their architecture series). This gives managed-service reliability without cloud dependency for real-time analytics.

3. **Kafka + ClickHouse in one platform** [確認済み]: Instaclustr offers both Managed Kafka and Managed ClickHouse. The ClickHouse Kafka Connect Sink connector is documented and bundled. Single vendor for both streaming and analytics on-prem.

4. **FSx for ONTAP + ClickHouse integration** [確認済み]: Instaclustr has published a blog specifically about "How FSx for ONTAP and Managed ClickHouse enhance lakehouse analytics" — directly validating this architecture pattern.

5. **Amazon Q + ClickHouse + Kafka + ONTAP** [確認済み]: Instaclustr published a resource about integrating Amazon Q with ClickHouse, Kafka, and ONTAP — further validating the AI analytics path.

### Why Two Phases / 2フェーズに分ける理由

- On-premises hardware is not yet available
- AWS PoC can validate data flow patterns immediately
- Phase A findings inform Phase B on-premises sizing
- Edge devices (Raspberry Pi) are in parallel development in a separate repository
- The architecture must work in both modes (portable design)

## Consequences / 結果

### Positive / ポジティブ

- Unified NetApp ecosystem: ONTAP (on-prem origin) + FlexCache (AWS cache) + Instaclustr (Kafka + ClickHouse)
- **No data duplication for payloads** — FlexCache provides on-demand access without full copy
- On-premises real-time analytics without cloud latency for factory dashboards
- Managed service reduces operational burden even on-premises
- AWS Databricks receives governed, replicated structured data (Kafka) for AI/ML
- AI/ML workloads access payloads via FlexCache (fetch on demand, cache locally)
- Single source of truth for payload data (on-premises ONTAP)
- Write-back mode (GA May 2025) enables bidirectional workflows if needed
- Architecture is testable in AWS-only mode before hardware arrives
- Lower AWS storage costs (cache size << full dataset size)

### Negative / ネガティブ

- Increased complexity (on-prem + cloud networking, replication, monitoring)
- Instaclustr on-prem requires customer-provided hardware (servers, network, power)
- Kafka replication adds latency for structured data reaching Databricks (acceptable for governed analytics)
- FlexCache cache misses incur WAN latency (first access to cold data is slow)
- VPN/Direct Connect bandwidth becomes a bottleneck for large payload cache fills
- Two environments to maintain during transition period
- Cost of both on-prem infrastructure + AWS services (but reduced by no data duplication)

## Risks / リスク

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| On-prem hardware procurement delayed | Medium | Medium | Continue Phase A on AWS; portable design |
| Instaclustr ClickHouse on-prem not GA | Low | High | Verify availability with Instaclustr SE; fallback to self-managed |
| Network latency on-prem → AWS too high for FlexCache | Medium | Medium | Size FlexCache cache appropriately; pre-warm cache for known workloads |
| VPN/Direct Connect bandwidth insufficient for cache fills | Medium | Medium | Evaluate Direct Connect 1/10 Gbps; batch pre-warm during off-hours |
| Kafka replication data loss | Low | High | MirrorMaker 2 with acks=all; monitor lag |
| FlexCache cache eviction during active ML training | Medium | Medium | Size cache volume for working set; pin frequently accessed data |
| Edge project integration complexity | Medium | Medium | Define clear API contract between repos |

## Design Review Notes / 設計レビューノート

> Notes recorded while checking this decision against the design concerns listed in [design concern checklist](../en/08_design_concern_checklist.md). Self-review, not external review.
>
> 本決定を[設計論点チェックリスト](../en/08_design_concern_checklist.md)に列挙した設計上の論点に照らして確認した際のメモ。セルフレビューであり、外部レビューではない。

- **Architecture soundness**: Phased approach reduces risk. AWS-first validates patterns before committing to on-prem hardware. Clear separation: real-time on-prem, governed analytics in cloud.
- **Edge and factory fit**: On-premises Kafka + ClickHouse addresses factory latency requirements. Edge devices (Raspberry Pi) connect locally. Separate repo for edge is practical.

- **Storage fit**: FlexCache is the correct pattern for avoiding data duplication. Origin on-prem with cache in AWS eliminates 2nd/3rd copies. Write-back mode (GA May 2025) enables future bidirectional use. SnapMirror reserved for DR only, not primary data path.

## Design Principle Summary / 設計原則サマリー

### Data Duplication Minimization / データ多重持ち排除

| Data Type | Origin | AWS Access Method | Copies in AWS |
|-----------|--------|-------------------|---------------|
| Structured events (Kafka) | On-prem Kafka | Kafka replication to MSK | 1 replica (necessary for Databricks access) |
| Payloads (images, video, docs) | On-prem ONTAP | **FlexCache (cache only)** | 0 permanent copies (cache evicts by LRU) |
| Curated analytics (Delta tables) | AWS S3 (produced by Databricks) | Native S3 | 1 (this is the derived/governed output) |
| ClickHouse hot analytics | On-prem ClickHouse | Not replicated to AWS | 0 in AWS |

**Result**: Only the Kafka event stream is replicated to AWS (necessary for Databricks ingestion). Payloads are never fully copied — FlexCache provides on-demand access with automatic eviction. Delta tables on S3 are derived/curated outputs, not copies of source data.
