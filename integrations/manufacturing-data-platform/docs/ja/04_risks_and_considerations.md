## 設計分析で特定されたリスク

以下のリスクは 07 の設計分析によって特定された
（詳細は [初回設計分析](07_initial_design_analysis.md) を参照）。
ペルソナ番号は分析を整理するための**役割ベースのアーキタイプ**であり、本設計を
レビューした人物を指すものではない。

### RSK-014: エッジバッファリング未設計（エッジと工場適合性）

- **説明:** Kafka に到達不能な場合のエッジデバイス向けストアアンドフォワードまたはローカルバッファリング機構が設計されていない。工場ネットワークは断続的になり得る。
- **影響:** 高 — エッジとクラウド間のネットワーク分断時のデータ損失
- **可能性:** 高（工場ネットワークはクラウドより本質的に信頼性が低い）
- **深刻度:** 高
- **軽減策:** エッジバッファリングの設計（ローカル MQTT 永続化、ファイルシステムキュー、または組み込み Kafka）。TSK-002 で対処。
- **ステータス:** 未設計 — PoC 実行前に Must Fix

### RSK-015: ClickHouse/Databricks データ乖離（アーキテクチャの妥当性）

- **説明:** ClickHouse と Databricks は同じ Kafka トピックから消費するが独立して処理する。処理セマンティクス（少なくとも1回 vs 正確に1回）、タイミング、障害によりデータ件数と状態が乖離する可能性がある。
- **影響:** 中 — リアルタイムビューとガバナンス付きビュー間で分析結果が不整合
- **可能性:** 中
- **深刻度:** 中
- **軽減策:** (1) データ整合性チェック戦略の定義。(2) リアルタイム（ClickHouse）vs ガバナンス（Databricks）の乖離を意図的として受容。(3) PoC 検証で定期的な整合性チェック。
- **ステータス:** 受容済みトレードオフ；監視戦略が必要

### RSK-016: ペイロード整合性検証ギャップ（エッジと工場適合性）

- **説明:** FSx for ONTAP 上のペイロードファイルが完全で、破損しておらず、Kafka メタデータイベントに記録されたチェックサムと一致することを自動的に検証する仕組みがない。
- **影響:** 中 — Delta テーブルから参照される破損または不完全なペイロード
- **可能性:** 中（ファイル転送は無音で失敗し得る）
- **深刻度:** 中
- **軽減策:** (1) アップロード後のチェックサム検証。(2) ペイロードアップロード確認後にのみ Kafka メタデータイベントを発行。(3) 定期的な整合性スキャンジョブ。(4) PoC で TSK-012 により検証。
- **ステータス:** 設計と PoC 検証が必要

### RSK-017: FSx for ONTAP 過剰ポジショニングリスク（ストレージ適合性）

- **説明:** FSx for ONTAP がネイティブ S3 の方がシンプルで安価な役割に配置される可能性がある。PoC のペイロードストレージレイヤーの過剰設計リスク。
- **影響:** PoC では低（管理可能なコスト）；本番信頼性では中
- **可能性:** 中
- **深刻度:** 低
- **軽減策:** (1) FSx for ONTAP が価値を追加する場所とネイティブ S3 で十分な場所を明確に定義。(2) 正直なトレードオフ分析を文書化（DEC-005）。(3) PoC で同一操作の S3 vs FSx for ONTAP 比較を含める。
- **ステータス:** 認知済み；ADR-003 と DEC-005 で対処

## 技術リスク

### RSK-001: Unity Catalog における S3 互換外部ロケーションの非対応

- **説明:** Unity Catalog 外部ロケーションはネイティブ Amazon S3、Azure ADLS、GCS、Cloudflare R2 のみサポート。S3 互換エンドポイント（ONTAP S3、MinIO）は非サポート。
- **影響:** 高 — Delta Lake テーブルを ONTAP S3 経由で FSx for ONTAP に格納不可
- **可能性:** 確認済み（リスクではなく制約）
- **深刻度:** アーキテクチャ設計に対して致命的；設計決定 DEC-001 で既に軽減
- **軽減策:** Delta テーブルはネイティブ Amazon S3 上にのみ格納。FSx for ONTAP はペイロードストレージのみ。
- **ステータス:** 設計により軽減済み

### RSK-002: ClickHouse Spark コネクターの成熟度

- **説明:** ClickHouse Spark コネクターはコミュニティ保守であり、特定の Databricks Runtime バージョンとのバージョン互換性問題がある可能性。
- **影響:** 中 — ClickHouse→Databricks バッチ読み取りが失敗またはパフォーマンス低下
- **可能性:** 中
- **深刻度:** 低（ClickHouse→Databricks は二次パス；主要取り込みは Kafka 経由）
- **軽減策:** (1) PoC でコネクター互換性をテスト。(2) S3 エクスポートをフォールバックパターンとして使用。(3) ClickHouse→Databricks パスはオプションとして維持。
- **ステータス:** PoC 検証が必要

### RSK-003: ClickHouse から ONTAP S3 への階層化ストレージ性能

- **説明:** ONTAP S3 をバックエンドとする ClickHouse S3 階層化ストレージは公開検証されていない。パフォーマンス特性がネイティブ S3 と異なる可能性。
- **影響:** 中 — コールド階層クエリが予想より遅い可能性
- **可能性:** 中
- **深刻度:** 中
- **軽減策:** (1) PoC で代表的なクエリパターンにより検証。(2) コールド階層レイテンシをネイティブ S3 とベンチマーク。(3) コールド階層のネイティブ S3 フォールバックを準備。
- **ステータス:** PoC 検証が必要

### RSK-004: ストリーミングパイプライン障害復旧の複雑性

- **説明:** Kafka→ClickHouse と Kafka→Databricks ストリーミングパイプラインは、チェックポイント管理と障害復旧手順の連携が必要。
- **影響:** 中 — 障害時のデータ損失または重複
- **可能性:** 低（十分に文書化されたパターン）
- **深刻度:** 中
- **軽減策:** (1) Structured Streaming は Delta Lake への正確に1回を提供。(2) ClickHouse Kafka エンジンは ReplacingMergeTree による重複排除付き少なくとも1回。(3) 復旧ランブックを文書化。
- **ステータス:** 設計により軽減；PoC で検証

### RSK-005: ネットワーク接続性の複雑性

- **説明:** 複数コンポーネント（MSK、ClickHouse、Databricks、FSx for ONTAP）が VPC 内または VPC 間でプライベートネットワーク接続性を必要とする。
- **影響:** 高 — ネットワーク設定ミス時にコンポーネント間通信不可
- **可能性:** 中
- **深刻度:** 高
- **軽減策:** (1) 全コンポーネントを同一 VPC にデプロイまたは VPC ピアリング使用。(2) セキュリティグループルールを文書化。(3) S3/AWS サービス向け VPC エンドポイント使用。(4) PoC で接続性を最初に検証。
- **ステータス:** 慎重な PoC セットアップが必要

## 運用リスク

### RSK-006: マルチコンポーネント運用複雑性

- **説明:** MSK + ClickHouse + Databricks + FSx for ONTAP の運用には、複数マネージドサービスにまたがる多様な専門知識が必要。
- **影響:** 高 — クロスコンポーネント問題のトラブルシューティングが困難
- **可能性:** 高
- **深刻度:** PoC では中、本番では高
- **軽減策:** (1) 可能な限りマネージドサービスを使用。(2) 可観測性の集約。(3) 運用ランブックの文書化。
- **ステータス:** PoC では受容；本番の主要考慮事項

### RSK-007: コスト見積もりの不確実性

- **説明:** MSK + ClickHouse + Databricks + FSx for ONTAP の複合コストは負荷テストなしでは正確に見積もり困難。
- **影響:** 中 — PoC 予算を超過する可能性
- **可能性:** 中
- **深刻度:** 中
- **軽減策:** (1) 最小サイジングで開始。(2) コストアラートを設定。(3) サーバーレス/オンデマンドを可能な限り使用。(4) PoC 開始前にコストモデルを見積もる。
- **ステータス:** PoC 前のコストモデルが必要

### RSK-008: エッジデバイスペイロードアップロードの信頼性

- **説明:** エッジ/工場から FSx for ONTAP への大容量ファイルアップロード（画像、動画）がネットワーク不安定により失敗する可能性。
- **影響:** 中 — ペイロードデータ損失
- **可能性:** 中（工場ネットワークは不安定になり得る）
- **深刻度:** 中
- **軽減策:** (1) 指数バックオフ付きリトライの実装。(2) 整合性検証にチェックサム使用。(3) ペイロードアップロード確認後にのみ Kafka メタデータイベント送信。(4) ローカルエッジバッファリング。
- **ステータス:** PoC 検証が必要

## ガバナンスリスク

### RSK-009: Unity Catalog と FSx for ONTAP 間の分割ガバナンス

- **説明:** 構造化データは Unity Catalog が管理。非構造化ペイロードは FSx for ONTAP 権限が管理。分割ガバナンスモデルを生成。
- **影響:** 中 — 不整合なアクセス制御、監査ギャップ
- **可能性:** 高（アーキテクチャに内在）
- **深刻度:** 中
- **軽減策:** (1) どのシステムが何を管理するか文書化。(2) アクセスポリシーを整合。(3) 監査ログの集約（CloudTrail + ONTAP 監査）。(4) ペイロードアクセスは Delta テーブル権限と FSx 権限の両方を要求。
- **ステータス:** 受容済みトレードオフ；明確に文書化

### RSK-010: ペイロード URI 整合性

- **説明:** Delta テーブルは FSx for ONTAP を参照する payload_uri を含む。ペイロードが移動、リネーム、削除された場合、参照が古くなる。
- **影響:** 中 — 壊れた参照が分析失敗を引き起こす
- **可能性:** 中
- **深刻度:** 中
- **軽減策:** (1) 不変ペイロードストレージ（ホットパスではライトワンス、リネーム/削除なし）。(2) バージョニングに Snapshot 使用。(3) 定期的な URI 検証ジョブ。(4) 整合性検証にチェックサムを含める。
- **ステータス:** PoC での設計検証が必要

## ベンダー/製品リスク

### RSK-011: ClickHouse Cloud の可用性と価格変更

- **説明:** ClickHouse Cloud は比較的新しいマネージドサービス。料金モデルと機能の可用性が変更される可能性。
- **影響:** 低
- **可能性:** 低
- **深刻度:** 低
- **軽減策:** (1) アーキテクチャは ClickHouse Cloud に固定されていない。(2) セルフマネージドまたは BYOC が代替。(3) ClickHouse 製品ロードマップを監視。
- **ステータス:** 受容

### RSK-012: Confluent Tableflow リージョン可用性

- **説明:** Confluent Tableflow は全リージョンまたは全 Kafka デプロイタイプ（セルフマネージド MSK 等）で利用可能でない可能性。
- **影響:** 低 — カスタム Structured Streaming にフォールバック（実績あり）
- **可能性:** 中
- **深刻度:** 低
- **軽減策:** (1) 主要アプローチは Databricks Structured Streaming（常に利用可能）。(2) Tableflow は Confluent Cloud ユーザー向けのオプション強化。
- **ステータス:** 受容；Tableflow はオプション

## 機密性リスク

### RSK-013: 公開リポジトリコンテンツ安全性

- **説明:** 全プロジェクトコンテンツが公開 GitHub リポジトリに公開される。機密情報の偶発的含有はリスク。
- **影響:** 高 — レピュテーション損害、NDA 違反
- **可能性:** 低（適切なレビュープロセスがあれば）
- **深刻度:** 高
- **軽減策:** (1) 全ドキュメントの機密性レビューチェックリスト。(2) 実顧客/パートナー名なし。(3) 合成データのみ。(4) シークレット検出の pre-commit フック。(5) 07 の機密性チェック。
- **ステータス:** 積極的軽減；継続的な注意が必要
