## Part 3 — Snowflake と FSx for ONTAP S3 Access Points

2026 年 5 月公開。2026-09-13 にリポジトリと突き合わせて確認。

記事の中心的な主張は妥当であり変更はない。ステージに `AWS_ACCESS_POINT_ARN` がなければ `LIST` は成功し `SELECT` は access denied で失敗する。設定すれば読み取りとガバナンスの経路が機能する。以下はいずれもそこには触れない。訂正対象は副次的な主張で、うち 3 件は記事を基に構築する人を誤らせる。

### C-01 — 根拠を欠いたまま推奨として提示された取り込み経路

| | |
|---|---|
| **深刻度** | 高 |
| **記事への反映** | ✅ 2026-09-14 |

記事の「Snowpipe Alternatives」節は **「Option 1: FPolicy → Lambda → SNS → Snowpipe REST API」** に **(Recommended)** を付け、レイテンシを「Seconds (<30s from file write to Snowflake availability)」としている。

問題は 3 つある。

1. **`<30s` という数値に裏付けとなる検証記録がない。** 本リポジトリで測定していたのはポーリング型 Lambda で、書き込みから通知まで 2.1 秒（スケジューラ待ちを除く）。実際の検知遅延はスケジュール間隔 + 約 2 秒である。FPolicy 自体のレイテンシは、ここでは測定していない。

> **この項目自体が誤っており、訂正する（2026-09-14）。** 当初は「FPolicy はイベントソースとして一度もライブで実行していない」と書いていた。**実行している。** 姉妹プロジェクト `fsxn-observability-integrations` が、同一 AWS アカウント上で ECS Fargate の外部 FPolicy サーバ（プロトコル 1.2）を用いて 72 時間のセッションを維持し、NFSv3 と SMB の通知を 0.3 秒で測定している。未検証と書いたのは、本リポジトリがどこを見たかという話であって、機構についての事実ではなかった。
>
> この訂正が重要なのは、同プロジェクトがより鋭い事実を確立しており、本ページがそれを運んでいなかったからである。**FPolicy は S3 Access Point 経由の操作を一切検知しない。** アクセスポイント経由のデータプレーン呼び出し 9 件で通知は 0 件、同一セッション・同一ボリュームに対するファイルプロトコルの対照は通知された。単に通知されないだけではない。`mandatory=true` と同期エンジンの構成で、NFSv3 の書き込みは `Permission denied` で拒否される一方、アクセスポイントの PUT / GET / LIST / DELETE はすべて成功した。つまりこの経路は FPolicy のゲートを通過していない。構造的な理由は、FPolicy イベントが受け付ける `protocol` が `cifs` / `nfsv3` / `nfsv4` の 3 値のみで、オブジェクトアクセスに対応する値が存在しないことである。ONTAP 9.18.1P5 で再確認し、`s3` / `object` / `http` はいずれも HTTP 400 で拒否された。記録: [イベントソースとしての FPolicy](../../verification-pack/fpolicy-event-source/evidence/2026-09-14/evidence-record.yaml)。
2. **描かれたトポロジではメッセージが届かない。** Snowflake のマネージド SQS キューを自分で subscribe することはできず、キューは Snowflake のアカウントにあるため `PendingConfirmation` のまま留まる。成立する形は pipe に `AWS_SNS_TOPIC` を設定して Snowflake 自身に subscribe させることである。
3. **この経路の公開成果物に後から 6 件の不備が見つかっており**、うち 2 件は無言のデータ損失を起こす。

**正しい記述。** スケジュール実行の取り込みには **Snowflake Task による `COPY INTO`** を使う（記事の Option 2 であり、これが Option 1 であるべき）。検証済みで、合成通知も SNS トピックポリシーも不要で、ポーリングウィンドウでは得られない exactly-once を Snowflake のロード履歴が与える。

**FPolicy が適する範囲と適さない範囲。** NFS / SMB 経由で届くファイルに対しては機能するイベントソースであり、アクセスポイント経由で届くファイルには盲目である。後者は本リポジトリのすべての統合が読み取りに使っている面である。したがって適合するかどうかは、Bronze 層をどう**書き込む**かで決まり、どう読むかでは決まらない。通知が飛ぶ構成であっても、取り込み設計は次を引き受ける必要がある。外部 FPolicy サーバの運用、IP で登録されるエンジンをタスク置換時に再登録する仕組み、再起動時の約 2 分のイベント欠落窓、そして NFSv3 の write-complete を既定で 5 秒保留すること。可観測性にとって再起動の欠落窓はログの穴だが、取り込みにとっては読み込まれないファイルであり、欠落を記録するものがどこにもない。FPolicy が価値を持つのは、検知が本当にサブ秒でなければならず、かつすべての書き込みがファイルプロトコル経由で届く場合である。合成通知によるイベント駆動取り込みはエンドツーエンドで検証済み（通知からロード済み行まで約 0.5 秒）だが、4 条件の同時成立を要し、どこにもエラーが出ない失敗モードを持つ。`s3.bucket.name` にアクセスポイントの ARN（エイリアスではなく）が入ると、Snowpipe はメッセージを受理して破棄し、pipe は正常と報告する。この経路の監視はオブジェクト数とロード行数の比較で組む必要がある。

参照: [Snowpipe 検証結果](../../integrations/snowflake/docs/ja/snowpipe-verification-results.md)。

### C-02 — Dynamic Table による External Table 参照の不可

| | |
|---|---|
| **深刻度** | 高 |
| **記事への反映** | ✅ 2026-09-14 |

記事は Partner Decision Card、「AI-Ready Data Product Journey」の図、「What to Tell Stakeholders」の 3 か所で `External Table → Dynamic Table` を示している。

**正しい記述。** 先に標準テーブルへ取り込む必要がある（`stage → COPY INTO 標準テーブル → Dynamic Table`）。その上で `TARGET_LAG = '60 seconds'` と `REFRESH_MODE = FULL` は仕様どおり動作する。`AUTO_REFRESH` が使えないため、Dynamic Table は上流メタデータの更新に依然として Task を必要とする。

### C-03 — アンロードは未解決の論点ではなく部分書き込みの危険

| | |
|---|---|
| **深刻度** | 高 |
| **記事への反映** | ✅ 2026-09-14 |

記事は「PutObject (via COPY INTO unload)」を **⚠️ TBD** とし「FSx S3 AP supports PutObject ≤5GB」と注記し、後段でアンロードは「未検証」としている。 <!-- allow:naming: 訂正対象である公開記事からの逐語引用 -->

**正しい記述。** 検証済みであり、最悪の形で失敗する。`COPY INTO @stage` は拒否されない。オブジェクトは正常な状態で書き込まれ、その後 FSx for ONTAP が暗号化を `aws:fsx` と報告するため `Remote upload failed checksum validation` で文が失敗する。**呼び出し側には失敗が返るのに、完全なオブジェクトが残る。** `ENCRYPTION = (TYPE = 'AWS_SSE_S3')` を設定しても解決せず、代わりに文がハングする。アクセスポイント経由のステージにアンロードを試したことがあるなら、対象プレフィックスを列挙して孤立オブジェクトを削除すること。

サイズの注記も実務上重要な形で誤っている。上限は **2 つ**ある。単一の `PutObject`、および各 `UploadPart` は約 5 GiB が上限で、オブジェクト全体は約 50 GiB が上限。全体側の超過は全バイト転送後の `CompleteMultipartUpload` で初めて検出される。

### S-02 — Part 2 における撤回済み数値の外挿と実環境識別子の公開

| | |
|---|---|
| **深刻度** | 高 |
| **記事への反映** | ✅ 2026-09-14 |

Databricks の記事には別個の問題が 3 つあった。

1. **撤回済み数値の外挿。** Auto Loader の注記が、大きなディレクトリでは「秒ではなく分レベルの検知遅延を前提にせよ」と助言していた。これは 30〜80 倍の数値から導いたもので、測定ではない。再測定値と、スケールが未測定である旨の明示に置き換えた。同じ表にある Directory Listing の阻害は別の発見であり影響を受けない。
2. **ベンダー帰属 3 件。** 2 件は NFS マウントが「seccomp により設計上ブロックされる」と断定し、1 件は `access_point` フィールドが GA になったことがないと断定していた。観測可能な内容に置き換えた。`mount` は `EACCES` を返し、`strace` はサーバの拒否ではなくシステムコールの阻害を示す。フィールドは現行ドキュメントに存在しない（これは誰でも確認できる）。「設計上」はプラットフォーム側の性格づけとして、そう明示したうえで残している。
3. **実環境の識別子。** プライベートな NFS サーバアドレスがコマンド出力 13 か所に現れ、VPC ID 2 件、ピアリング接続 ID、VPC エンドポイント ID も含まれていた。RFC 5737 のドキュメント用レンジとプレースホルダに置き換えた。置換した事実を記事に明記している。出力の中の識別子を無言で書き換えると証拠が変わるためで、ポート・エラー文字列・システムコールの結果・所要時間は変更していないことも併記した。

### S-03 — 線形外挿による推奨経路の優位の過大表示

| | |
|---|---|
| **深刻度** | 中 |

### 訂正ではなく加筆: SnapMirror の検証結果

AWS Backup のクロスリージョン記事は、SnapMirror 宛先が `DP` ボリュームでありバックアップ対象にできないことを説明している。これは正しく、変更していない。同時にそこは、読者が「`DP` ボリュームでは他に何もできない」と結論しやすい箇所でもある。そこで 2026-09-13 の結果を加筆した。レプリケーション稼働中のレプリカをアクセスポイント経由で読み取り提供でき、判定はボリューム種別ではなく junction path で行われる。この記事に誤りはなく、これは加筆である。
