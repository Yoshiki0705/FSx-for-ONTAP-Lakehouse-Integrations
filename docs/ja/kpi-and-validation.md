# KPI と PoC 検証ガイド

## 概要

本ドキュメントは、FSx for ONTAP Lakehouse 統合 PoC の測定可能な成功基準を定義します。明確な KPI がなければ、PoC の成功/失敗を評価することは不可能です。各メトリクスには測定方法と目標範囲を含みます。

## コア KPI

### 1. クエリレイテンシ

| メトリクス | 定義 | 測定方法 | 目標（Good ティア） | 目標（Best ティア） |
|--------|-----------|-------------------|-------------------|-------------------|
| コールドクエリレイテンシ | クエリ送信から最初の結果までの時間（キャッシュなし） | Athena/Databricks クエリ実行時間 | 1 GB スキャンで < 30 秒 | 1 GB スキャンで < 10 秒 |
| ウォームクエリレイテンシ | FSx for ONTAP NVMe/メモリキャッシュにデータがある場合の時間 | 繰り返しクエリ実行時間 | 1 GB スキャンで < 10 秒 | 1 GB スキャンで < 5 秒 |
| メタデータクエリレイテンシ | スキーマ/パーティション検出の時間 | Glue Catalog API レスポンス時間 | < 5 秒 | < 2 秒 |

**測定方法**:
```sql
-- Athena: コンソールまたは API でクエリ実行時間を確認
SELECT query_execution_id, 
       total_execution_time_in_millis,
       data_scanned_in_bytes
FROM information_schema.__query_log__
WHERE query LIKE '%your_table%'
ORDER BY submission_date_time DESC;
```

### 2. スループット

| メトリクス | 定義 | 測定方法 | 目標 |
|--------|-----------|-------------------|--------|
| 読み取りスループット | テーブルスキャン中の持続 MB/s | CloudWatch `DataReadBytes` / クエリ時間 | FSx for ONTAP プロビジョンドスループットの ≥ 80% |
| 書き込みスループット | ETL 書き戻し中の MB/s | CloudWatch `DataWriteBytes` / 書き込み時間 | FSx for ONTAP プロビジョンドスループットの ≥ 50% |
| 同時クエリスループット | 同時負荷下の集約スループット | 複数同時クエリ | プロビジョンド上限まで線形スケーリング |

**注意**: S3 Access Points 経由の S3 API スループットは FSx for ONTAP ファイルシステムのプロビジョンドスループット容量に依存します。ネイティブ S3 のスループットとは同等ではありません。（[ソース](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/performance.html)）

### 3. スキャンあたりのコスト（TB 単位）

| メトリクス | 定義 | 測定方法 | 目標 |
|--------|-----------|-------------------|--------|
| Athena コスト/TB | スキャンした TB あたりの Athena クエリコスト | $5/TB（Athena 料金）+ FSx for ONTAP スループットコスト | 合計 < $10/TB |
| ストレージコスト/TB | TB あたりの月額ストレージコスト | FSx for ONTAP SSD + キャパシティプール料金 | S3 Standard + ETL パイプラインコストと比較 |
| 総所有コスト | ストレージ + コンピュート + データ転送 | 月額請求分析 | 現在の NAS + S3 コピーパイプラインコスト未満 |

**コスト比較フレームワーク**:
```
Current state cost:
  NAS storage: $X/TB/month
  + S3 copy storage: $Y/TB/month  
  + ETL pipeline compute: $Z/month
  + Data transfer: $W/month
  = Total: $(X+Y+Z+W)/month

FSx for ONTAP S3 AP state cost:
  FSx for ONTAP storage: $A/TB/month
  + Analytics compute: $B/month
  + No S3 copy: $0
  + No ETL pipeline: $0
  = Total: $(A+B)/month

Savings = Current - FSx for ONTAP S3 AP
```

### 4. データ鮮度

| メトリクス | 定義 | 測定方法 | 目標 |
|--------|-----------|-------------------|--------|
| 書き込みからクエリまでのレイテンシ | NFS/SMB 書き込みから S3 AP クエリ可視化までの時間 | NFS 経由でファイル書き込み、即座に S3 AP 経由でクエリ | ほぼゼロ（同一ボリューム、同一データ） |
| カタログ更新レイテンシ | ファイル作成から Glue Catalog 認識までの時間 | Glue Crawler 実行時間またはイベント駆動更新 | < 5 分（Crawler）または < 1 分（イベント） |

**主要な利点**: S3 Access Points は FSx for ONTAP ボリュームから直接読み取るため、NFS/SMB 経由で書き込まれたデータは S3 API 経由で即座に可視化されます。同期遅延なし。

### 5. 回避されたデータコピー数

| メトリクス | 定義 | 測定方法 | 目標 |
|--------|-----------|-------------------|--------|
| コピー数削減 | 排除された冗長データコピーの数 | 現在のデータコピーの棚卸し vs. 新アーキテクチャ | ≥ 50% 削減 |
| ストレージ削減 | 排除された重複ストレージの TB | 排除されたコピーサイズの合計 | $/月で定量化 |
| パイプライン排除 | 不要になった同期/コピーパイプラインの数 | 不要になった ETL ジョブの数 | ≥ 1 パイプライン排除 |

### 6. 目標復旧時間（RTO）/ 目標復旧時点（RPO）

| メトリクス | 定義 | 測定方法 | 目標 |
|--------|-----------|-------------------|--------|
| Snapshot RTO | スナップショットからのボリューム復元時間 | タイム計測付きスナップショット復元テスト | < 5 分 |
| Snapshot RPO | 最大データ損失ウィンドウ | スナップショットスケジュール頻度 | ≤ 1 時間（時間単位スナップショット） |
| SnapMirror RTO | DR リージョンへのフェイルオーバー時間 | タイム計測付きフェイルオーバーテスト | < 15 分 |
| SnapMirror RPO | レプリケーションラグ | SnapMirror ラグメトリクス | < 15 分（非同期）または 0（同期） |

### 7. アクセスポリシーレビュー時間

| メトリクス | 定義 | 測定方法 | 目標 |
|--------|-----------|-------------------|--------|
| ポリシー監査時間 | 全アクセスポリシーのレビュー・検証時間 | IAM + AP + ファイルシステム権限の手動レビュー | アクセスポイントあたり < 1 時間 |
| 権限変更時間 | アクセス付与/取り消しの時間 | リクエストから有効化までの時間 | < 30 分 |
| コンプライアンスレポート生成 | アクセス監査レポートの生成時間 | CloudTrail クエリ + レポート生成 | < 1 時間 |

## PoC 成功基準テンプレート

### フェーズ 1: 接続性検証（Week 1）

| 基準 | 合格条件 | テスト方法 |
|-----------|---------------|-------------|
| S3 AP 作成 | アクセスポイントが AVAILABLE 状態 | `aws fsx describe-s3-access-points` |
| 基本読み取り | AP エイリアス経由で GetObject 成功 | `aws s3 cp s3://AP-ALIAS/test.txt .` |
| 基本書き込み | AP エイリアス経由で PutObject 成功 | `aws s3 cp test.txt s3://AP-ALIAS/` |
| オブジェクト一覧 | ListObjectsV2 が期待されるファイルを返す | `aws s3 ls s3://AP-ALIAS/` |
| IAM 認可 | 権限のないロールが拒否される | AP 権限のないロールでテスト |
| ファイルシステム認可 | 読み取り専用ユーザーが書き込み不可 | 読み取り専用 AP ユーザーで PutObject テスト |

### フェーズ 2: 分析統合（Week 2）

| 基準 | 合格条件 | テスト方法 |
|-----------|---------------|-------------|
| Glue Crawler | Glue Catalog にテーブル登録 | Crawler 実行、カタログでテーブル確認 |
| Athena クエリ | SQL クエリが正しい結果を返す | 登録テーブルに対して SELECT 実行 |
| クエリパフォーマンス | データセットサイズに対するレイテンシ目標を達成 | クエリ実行時間を測定 |
| データ鮮度 | 新しいファイルが SLA 内でクエリに可視 | NFS 経由で書き込み、Athena 経由でクエリ |

### フェーズ 3: 本番準備（Week 3-4）

| 基準 | 合格条件 | テスト方法 |
|-----------|---------------|-------------|
| 同時アクセス | N 同時クエリで劣化なし | 並列クエリによる負荷テスト |
| セキュリティ検証 | 両レイヤーで不正アクセスが拒否 | IAM + ファイルシステムのペネトレーションテスト |
| 監査完全性 | 全アクセスイベントが CloudTrail に記録 | テスト期間の CloudTrail レビュー |
| リカバリテスト | RTO 目標内でのスナップショット復元 | タイム計測付き復元演習 |
| コスト検証 | 総コストが予算内 | 実績 vs. 予測コストの比較 |

## ビジネス KPI マッピング

技術 KPI は、経営層やビジネスステークホルダーが評価できるビジネス/運用メトリクスに変換する必要があります。

| 技術 KPI | ビジネス KPI | 回答されるビジネス上の問い |
|--------------|-------------|---------------------------|
| クエリレイテンシ（秒） | 分析リクエストから意思決定までの時間 | 「データに基づいてどれだけ速く行動できるか？」 |
| データ鮮度（書き込みからクエリまで） | 運用データ反映遅延 | 「最新のデータで意思決定しているか？」 |
| 回避されたデータコピー数 | ストレージコスト削減（$/月）+ 運用人件費削減 | 「コピーパイプラインを維持しないことでどれだけ節約できるか？」 |
| スループット（MB/s） | アナリスト生産性（クエリ/日） | 「チームは待たずに必要な分析をすべて実行できるか？」 |
| スキャンあたりのコスト（TB） | ビジネスインサイトあたりの分析コスト | 「各レポート/ダッシュボードのコストはいくらか？」 |
| RTO / RPO | 事業継続 SLA 準拠 | 「規制上の復旧コミットメントを満たせるか？」 |
| アクセスポリシーレビュー時間 | 監査対応時間（時間） | 「コンプライアンス監査にどれだけ迅速に対応できるか？」 |
| RAG 回答精度 | ナレッジワーカーの時間節約 | 「従業員はどれだけ速く情報を見つけられるか？」 |

### エグゼクティブダッシュボードメトリクス

CxO レポーティングでは、次の 4〜5 個のヘッドラインメトリクスに集約します。

| メトリクス | 内容 |
|---|---|
| コスト回避 | データコピーパイプライン排除により $X/月を節約 |
| Time-to-insight | Y 日から Z 時間に短縮 |
| コンプライアンス態勢 | データアクセスの 100% が CloudTrail で監査可能 |
| AI 準備度 | N 件のドキュメントが移行なしで AI/RAG にアクセス可能 |
| 運用リスク | DR テスト済み、RTO < 15 分、RPO < 1 時間 |

## 初期ユースケース選定

最初の Investment Case では、リスクを最小化しつつ測定可能性を最大化する ONE ユースケースを選択します。

### 決定: Enterprise IT RAG

以下の選定マトリクスに基づき、**Enterprise IT RAG** が推奨される最初のユースケースです。

```yaml
# Value Hypothesis (define BEFORE verification)
value_hypothesis:
  use_case: "Enterprise IT RAG"
  business_issue: "Incident responders spend too long searching for relevant runbooks and past incident reports"
  target_users: "L2 support engineers, SRE team, operations staff"
  data_source: "Runbooks, incident reports, architecture docs, FAQs on NFS/SMB file shares"
  
  expected_value:
    search_time_reduction: "30-50%"
    first_response_time_reduction: "20-30%"
    mttr_improvement: "10-15%"
  
  measurement:
    baseline_period: "30 days before PoC"
    measurement_period: "90 days"
    primary_kpi: "Mean time from incident start to relevant document found"
    secondary_kpis:
      - "MTTR (mean time to resolution)"
      - "User satisfaction (1-5 survey)"
      - "RAG answer accuracy (human review pass rate)"
  
  guardrails:
    data_risk: "Low (no PHI/PII in IT runbooks)"
    read_only: true
    human_review: "Required for first 30 days; optional after accuracy > 90%"
  
  decision_criteria:
    scale: "Search time reduced ≥ 30%; accuracy ≥ 85%; cost within budget"
    adjust: "Technically works but adoption < 50% or accuracy < 85%"
    stop: "No measurable improvement after 60 days"
  
  investment_case_timeline:
    benchmark_complete: "Week 2"
    security_test_complete: "Week 2"
    initial_cost_estimate: "Week 3"
    draft_investment_case: "Day 30 (based on initial usage data)"
    final_investment_case: "Day 90 (based on full measurement period)"
```

### 測定シーケンス

| ステップ | アクティビティ | タイムライン | アウトプット |
|------|----------|----------|--------|
| 1 | ベースライン KPI 測定（現在の検索時間、MTTR） | Week -2 〜 0 | ベースラインメトリクス |
| 2 | データ準備度評価 | Week 1 | 準備度スコア |
| 3 | FSx for ONTAP S3 AP + Athena/Bedrock デプロイ | Week 1-2 | 稼働環境 |
| 4 | 機能 + セキュリティ + ベンチマークテスト | Week 2 | エビデンス記録 |
| 5 | ユーザーパイロット（5-10 名） | Week 3-4 | 初期利用データ |
| 6 | 30 日レビュー + Investment Case ドラフト | Day 30 | Go/Adjust 判断 |
| 7 | 全ユーザー展開（Go の場合） | Day 30-60 | 広範な採用データ |

| 9 | 90 日 Scale/Adjust/Stop 判断 | Day 90 | 最終 Investment Case |

### 推奨される最初のユースケース

| 基準 | Enterprise IT RAG | 製造業メンテナンス | ヘルスケアリサーチ |
|-----------|:-:|:-:|:-:|
| PHI/PII リスク | 低 | 低 | 中（匿名化が必要） |
| ビジネス KPI の明確さ | 高（MTTR） | 高（ダウンタイム） | 中（研究アウトプット） |
| 30/60/90 日測定可能性 | 高 | 高 | 中 |
| データ準備度（一般的） | 高（NAS 上のドキュメント） | 中（混合フォーマット） | 低（パイプラインが必要） |
| ステークホルダーの複雑さ | 低 | 低 | 高（IRB、倫理） |
| **推奨優先度** | **#1** | **#2** | **#3** |

**推奨事項**: Enterprise IT RAG または製造業メンテナンスから開始してください。ヘルスケアは、低リスクのユースケースでガバナンスフレームワークが検証された後に続けるべきです。

### エグゼクティブ Investment Case インプット要件

Investment Case を作成する前に、以下の測定値を収集します：

| インプット | ソース | 必要な用途 |
|-------|--------|-------------|
| クエリレイテンシ（P50, P95） | ベンチマーク結果 | Time-to-insight の主張 |
| スループット（MB/s） | ベンチマーク結果 | キャパシティプランニング |
| データセットサイズとファイル数 | データ準備度評価 | ストレージコスト予測 |
| ストレージ + クエリ + インジェストコスト | AWS Cost Explorer + Athena 課金 | ROI 計算 |
| 運用工数（時間/週） | 運用チーム見積もり | TCO 比較 |
| データ鮮度（書き込みからクエリまで） | 機能テスト | 鮮度 SLA の主張 |
| エラー/障害率 | テスト結果 | 信頼性の主張 |
| セキュリティテスト結果 | ネガティブテストマトリクス | リスク態勢ステートメント |

### 90 日判断基準

Day 90 で、3 つの判断のいずれかを行います：

| 判断 | 基準 | 次のアクション |
|----------|----------|-------------|
| **Scale** | KPI 改善が確認された（≥ 目標）；リスクとコストが許容範囲内；ユーザー採用 > 50% | より多くのユーザー/データ/ユースケースに拡大；投資のためエグゼクティブに提示 |
| **Adjust** | 技術的には実現可能だが、データ品質、ユーザー採用、またはビジネスフィットに改善が必要 | 具体的なギャップを特定；30 日改善計画を定義；Day 120 で再評価 |
| **Stop** | KPI 改善が達成不可能；運用負荷が高すぎる；リスクが許容不可；コストが価値を超過 | 学びを文書化；環境をアーカイブ；投資を別方向に振り向け |

## PoC ガードレール

安全な実験を可能にするため、PoC 中に許可される範囲の明確な境界を定義します。

### PoC で許可されること

| アクティビティ | 条件 |
|----------|-----------|
| 読み取り専用分析（Athena, Glue Crawler） | 任意のデータ分類 |
| Glue ETL 読み取り + 書き戻し（Parquet） | Internal/Public データのみ |
| Bedrock RAG インジェスト | 匿名化済みドキュメントのみ |
| パフォーマンスベンチマーク | 合成データまたは公開データセット |
| セキュリティテスト（IAM 拒否検証） | 制御されたテストプリンシパル |
| スナップショット復元テスト | 非本番ボリューム |

### PoC で許可されないこと

| アクティビティ | 理由 |
|----------|--------|
| Delta Lake write / MERGE / compaction | 非サポート — 不整合な状態を生成する |
| 非本番環境での実際の PHI/PII | コンプライアンス違反リスク |
| Confidential/Regulated データに対するインターネットオリジン AP | 規制データに対するセキュリティ態勢が不十分 |
| テスト用の本番 AP ポリシー変更 | 本番アクセス中断のリスク |
| 定義されたコスト上限の超過 | 予算管理 |
| PoC アクセス認証情報の共有 | 監査証跡の完全性 |

### PoC コスト上限

開始前に最大許容 PoC コストを定義します：

| コンポーネント | 見積コスト（2 週間 PoC） |
|-----------|---------------------------|
| FSx for ONTAP (512 MB/s, 1 TB SSD) | 〜$800 |
| Athena クエリ（10 TB スキャン） | 〜$50 |
| Glue Crawler + ETL | 〜$20 |
| CloudTrail（S3 データイベント） | 〜$10 |
| **合計上限** | **< $1,000** |

### PoC 終了基準

| 結果 | アクション |
|---------|--------|
| フェーズ 1-2 の全基準合格 | フェーズ 3（本番準備）に進む |
| パフォーマンス目標未達 | FSx for ONTAP スループットサイジングを評価；より高いプロビジョニングで再テスト |
| セキュリティ検証失敗 | 進行前に調査・修正 |
| コストが上限を超過 | 停止してアーキテクチャを再評価 |
| 根本的な制限を発見 | 文書化して代替アプローチを評価 |

## 将来: Agentic AI 統合

AI が RAG から自律エージェントへ進化するにつれ、FSx for ONTAP S3 AP はエンタープライズファイルデータを AI エージェント向けのガバナンス付きデータアクセスレイヤーとして位置づけます。

### 潜在的な統合ポイント

| AI 機能 | FSx for ONTAP S3 AP の役割 | ステータス |
|--------------|---------------|--------|
| **Bedrock Knowledge Bases (RAG)** | 検索用ドキュメントデータソース | ✅ 利用可能（[チュートリアル](https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/tutorial-build-rag-with-bedrock.html)） |
| **Bedrock Agents (tool use)** | エージェントが S3 API ツール経由でドキュメントを取得 | アーキテクチャ的に実現可能（agent → S3 GetObject → AP → FSx） |
| **MCP 互換ツール** | 任意の MCP クライアント向け S3 ベースドキュメント取得ツール | アーキテクチャ的に実現可能（MCP tool wraps S3 GetObject） |
| **Athena クエリツール** | エージェントが Athena + Glue Catalog 経由でファイルデータに SQL 実行 | アーキテクチャ的に実現可能（agent → Athena → Glue → AP → FSx） |
| **マルチモーダル AI** | メディアファイルの画像/動画/音声分析 | アーキテクチャ的に実現可能（agent → GetObject → media file → model） |

### Agentic AI のガバナンス

AI エージェントがエンタープライズデータに自律的にアクセスする場合、次のガバナンスが重要になります。

| 統制 | 内容 |
|---|---|
| 読み取り専用アクセスポイント | エージェントはソースデータへの書き込みアクセスを持たない |
| スコープされた IAM ロール | エージェントごとの IAM ロールで最小限必要な権限のみ |
| 監査証跡 | 全エージェントデータアクセスを CloudTrail S3 データイベントで記録 |
| Human-in-the-loop | ビジネス判断に影響するエージェントアクションには人間の承認が必要 |
| レート制限 | 暴走エージェントが FSx for ONTAP スループットを圧迫することを防止 |
| データ分類認識 | エージェントはデータ分類の境界を尊重する |

### 戦略的ポジショニング

```
Today (2025):          Near-term (2026):           Future:
RAG on documents  →    Agents query structured  →  Autonomous agents
(Bedrock KB)           + unstructured data          with governed access
                       (Athena + Bedrock)           to enterprise files
```

FSx for ONTAP S3 AP は、データセキュリティと監査可能性が譲れない AI エージェントアーキテクチャに適した**ガバナンス付き、監査可能、読み取り専用のデータアクセスレイヤー**を提供します。

### Agentic AI ロードマップ（フェーズ別）

| フェーズ | 機能 | ビジネスユースケース | ガードレール | 人間の承認 | 終了基準 |
|-------|-----------|-------------------|-----------|----------------|---------------|
| **1. 読み取り専用 RAG** | FSx for ONTAP ドキュメント上の Bedrock Knowledge Base | ドキュメント検索、マニュアル/ポリシーの Q&A | 読み取り専用 AP、回答の人間レビュー | 全レスポンスに必須 | 精度 > 80%、ユーザー採用 > 50% |
| **2. RAG + クエリアシスタント** | RAG + Athena SQL 生成 | 「先月の生産データを見せて」→ SQL → 結果 | 読み取り専用 AP + Athena、クエリコスト制限 | データ変更クエリに必須 | クエリ精度 > 90%、コスト < 予算 |
| **3. エージェント支援分析** | マルチステップ: ドキュメント取得 → データクエリ → 要約 | 自動レポート生成、トレンド分析 | 読み取り専用 AP、実行時間制限、出力レビュー | レポート配布前に必須 | ドメインエキスパートによるレポート品質検証 |
| **4. マルチツールガバナンスエージェント** | エージェントが複数ツールを使用（S3, Athena, Bedrock, Lambda） | 複雑なリサーチワークフロー、クロスソース分析 | ツールごとの IAM スコーピング、レート制限、監査 | ビジネスインパクトのあるアクションに必須 | ワークフロー完了率 > 95% |
| **5. 人間承認付き自律** | エージェントがアクションを提案、人間が実行を承認 | 自動データパイプライン管理、異常対応 | 完全な監査証跡、ロールバック機能、SLA モニタリング | 不可逆アクションのみ承認必要 | 平均解決時間が > 50% 改善 |

| **エクスペリエンス KPI** | 技術者満足度 | アンケート | ≥ 4.0 |
| **リスク KPI** | 誤った手順の実行 | 誤った手順を引用したインシデントレポート | ゼロ |

### ヘルスケア: 研究文書検索

| レベル | メトリクス | 測定方法 | 目標 |
|-------|--------|-------------|--------|
| **ビジネス課題** | 研究者が関連研究の発見に時間をかけすぎている | 文献検索の時間/週 | ベースライン: X 時間/週 |
| **プロセス KPI** | ドキュメント発見時間 | クエリから関連ドキュメントセットまでの時間 | 70% 削減 |
| **アウトカム KPI** | 研究アウトプット | 提出論文数/四半期 | 20% 増加 |
| **エクスペリエンス KPI** | 研究者満足度 | アンケート | ≥ 4.0 |
| **リスク KPI** | 研究コンテキストでの PHI 露出 | 監査所見 | ゼロ |

## 組織採用モデル

成功するデプロイメントには、技術だけでなく組織的なアラインメントが必要です。

### 役割と責任

| 役割 | 責任 | エンゲージメントレベル |
|------|---------------|-----------------|
| **エグゼクティブスポンサー** | 予算承認、組織優先度、ブロッカー除去 | 月次レビュー |
| **ビジネスオーナー** | ユースケース定義、成功基準、ユーザー受入 | 週次チェックイン |
| **データオーナー** | データアクセス承認、分類、保持 | プロジェクトごとの承認 |
| **プラットフォームチーム** | FSx for ONTAP + S3 AP + 分析のデプロイ、運用、モニタリング | 日次運用 |
| **セキュリティ / ガバナンス** | ポリシーレビュー、アクセス承認、監査 | 変更ごとのレビュー |
| **AI プロダクトオーナー** | RAG ユースケース定義、精度評価、ガードレール管理 | 週次イテレーション |
| **ユーザーチャンピオン** | ビジネスユニット内での採用推進、フィードバック収集 | 継続的 |
| **フィードバックコミュニティ** | 利用フィードバック提供、問題報告、改善提案 | 継続的 |

### 採用ステージ

```
Stage 1: Pilot (1 team, 1 use case)
  → Prove value with minimal risk
  → 1-2 months

Stage 2: Expand (multiple teams, same use case)
  → Scale proven pattern
  → 2-3 months

Stage 3: Diversify (multiple use cases)
  → Add RAG, new data sources, new analytics
  → 3-6 months

Stage 4: Standardize (organization-wide platform)
  → Self-service, governance automated, value tracked
  → 6-12 months
```

## Agentic AI 自動化禁止ルール

AI エージェントが機能を獲得するにつれ、人間の承認なしに決して自動化してはならないことを明示的に定義します。

| ルール | 根拠 | 強制方法 |
|------|-----------|-------------|
| 本番データを自律的に削除・変更**しない** | 不可逆；データ損失リスク | エージェント用読み取り専用 AP；エージェント IAM に DeleteObject/PutObject なし |
| 人間の承認なしにアクセスポリシーを変更**しない** | セキュリティ態勢の変更 | SCP が PutAccessPointPolicy を管理者ロールのみに制限 |
| 臨床的または財務的な意思決定を自律的に実行**しない** | 規制および安全リスク | 全意思決定出力に Human-in-the-loop 必須 |
| 承認された境界外に規制データをエクスポート**しない** | コンプライアンス違反 | VPC-origin AP；承認なしのクロスリージョン/クロスアカウント不可 |
| 承認なしに不可逆ワークフローをトリガー**しない** | 元に戻せない | エージェントがアクションを提案；人間が実行を承認 |
| 監査ログをバイパス**しない** | コンプライアンス要件 | エージェント IAM ロールで CloudTrail を無効化不可 |
| エージェントの分類レベルを超えるデータにアクセス**しない** | データガバナンス | エージェントごとの IAM を特定の AP とプレフィックスにスコープ |
| 定義されたコスト/スループット制限を超過**しない** | 予算管理 | サービスクォータとエージェントアクティビティの CloudWatch アラーム |

### 強制メカニズム

| メカニズム | 防止する内容 |
|-----------|-----------------|
| AP 上の読み取り専用ファイルシステムユーザー | エージェントがデータを書き込み/削除できない |
| スコープされた IAM ロール（GetObject + ListBucket のみ） | エージェントがポリシーやインフラを変更できない |
| エージェントアカウント/OU の SCP | エージェントが権限昇格できない |
| スループットの CloudWatch アラーム | 暴走エージェントを検出してスロットリング |
| Bedrock ガードレール | 不適切なコンテンツをフィルタリング |
| 人間承認ゲート | 不可逆アクションに明示的な承認が必要 |
